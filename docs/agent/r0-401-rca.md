Evidencia del operador (auditoría de solo lectura). Este documento no se ejecutó contra PROD. No hay POST, replay, cambio de cron ni rotación de secretos.

Congelación R1: `640fa52`. SQL de auditoría: `supabase/scripts/audit_r0_prod_readonly.sql`.

## Diagnóstico

**Causa raíz (alta confianza):** el cron `whatsapp-followup-dispatcher` (job pg_cron con `has_unreplaced_placeholder=true` y sin `x-dispatcher-secret`) está definido como el script de operador [`fix_whatsapp_dispatcher_cron_anon.sql`](../../supabase/scripts/fix_whatsapp_dispatcher_cron_anon.sql) **sin sustituir** `PASTE_ANON_KEY`. Ese literal forma parte del `command` ejecutado cada minuto (`Authorization: Bearer PASTE_ANON_KEY`, `apikey: PASTE_ANON_KEY`). No es un comentario.

Cada minuto `pg_cron` marca `succeeded` porque `net.http_post` corre. La respuesta HTTP es 401: el Edge recibe el POST (`edge_execution_id` presente) y `dispatcherAuthorized` rechaza (token `PASTE_ANON_KEY` ≠ anon/service; no hay `x-dispatcher-secret`). Hasta 20 `whatsapp_followup_jobs` pendientes **no se reclaman** mientras dure este 401.

El otro cron (Vault `whatsapp_dispatcher_secret` en minúsculas, sin placeholder) coincide con [`schedule_whatsapp_inbound_worker.sql`](../../supabase/scripts/schedule_whatsapp_inbound_worker.sql) → `whatsapp-webhook?worker=1`. Su guarda devuelve **403**, no 401. Las 30 filas A3 en 401 apuntan al dispatcher, no al worker. Confirmar `jobname` en A1.

`gateway_error_code=null` **no** prueba capa Gateway. `verify_jwt=false`; un GET sin credenciales ya llegaba al runtime (405). La función, si rechaza, pone `x-whatsapp-auth-layer=edge_function` (no se leyó en A3). Siguiente lectura: esa cabecera, sin `content`.
